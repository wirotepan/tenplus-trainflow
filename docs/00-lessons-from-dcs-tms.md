# บทเรียนจาก DCS-TMS — สิ่งที่ TrainFlow จะไม่ทำซ้ำ

> ที่มา: โค้ด/เอกสารจริงของ `/data/WORKSPACE/dcs-tms` (M1–M8, ก.ค.–ส.ค. 2026) —
> `docs/m8-gap-analysis.md` · `docs/reviews/2026-07-20-code-review-serviceDate.md` ·
> `docs/adr/0001-planned-vs-actual-vehicle.md` · decision log ใน `CLAUDE.md`
> อ่านก่อนตัดสินใจเรื่องโครงสร้างข้อมูลหรือขอบเขตงานทุกครั้ง

**ตัวเลขที่ควรจำ:** หลังส่ง M1–M7 (ทำงานจริง รันบน production ได้) แล้วเอาไปเทียบกับ requirement
ที่ถอดจากประชุมลูกค้า 2 ชม. 37 นาที ผลคือ **ตรงกับที่ทำไว้เพียง 45–50%** ·
ต้องแก้ของเดิม 8 จุดใหญ่ (กระทบ DB ทุกหน้าจอ) · ของใหม่ล้วน 12 จุด · **ต้องถอดทิ้ง 2 จุด**

---

## L1 🔴 เก็บ requirement ไม่จบ แล้วรีบเขียนโค้ด

**อาการที่ dcs-tms เจอ** — ทำครบ 7 โมดูล ใช้งานได้จริง แต่พอประชุมลูกค้าเต็มรูปแบบ (ส.ค.)
กลับพบว่าโครงสร้างหลักผิดไปครึ่งระบบ ต้องทำ M8 ทั้งเดือนเพื่อไล่แก้

**ต้นเหตุ** — เริ่มจากสรุปประชุมย่อ ไม่ได้ขอ *เอกสารจริงที่ลูกค้าใช้อยู่* และไม่ได้ไล่ถามเคสจริงจนจบก่อนลงมือ

**TrainFlow ทำแทน**
- เฟส 1 ต้องมี **คำถามเปิดที่ติดธง 🔴** และ **ห้ามเริ่มเขียนโค้ดจนกว่าจะได้คำตอบ** (ตอนนี้คือ Q1–Q4 ใน `01-requirements.md`)
- ขอ **เอกสารจริงทุกใบก่อนออกแบบหน้าจอที่เกี่ยวข้อง**: ใบเสนอราคา · ใบลงชื่อเข้าอบรม · แบบประเมิน ·
  **วุฒิบัตรของจริง** · **รูปเล่มรายงานที่เคยส่งลูกค้า** · Excel ต้นทุนที่ใช้อยู่
- ทุก FR มีรหัส (`A1`, `C3`, …) ใช้อ้างอิงข้ามเอกสาร ตั้งแต่วันแรก ไม่ใช่มาใส่ทีหลัง

## L2 🔴 Cardinality ผิด = รื้อทั้งระบบ

**อาการ** — ออกแบบไว้ว่า *1 ออเดอร์ = 1 เที่ยววิ่ง* แต่ความจริงคือ **1 ออเดอร์ = N เที่ยว**
gap analysis จัดข้อนี้เป็น "งานใหญ่สุด — **ห้ามเริ่มก่อนยืนยัน**" เพราะกระทบ DB + ทุกหน้าจอ + ใบวางบิล

**TrainFlow — จุดเสี่ยงเดียวกันที่ต้องยืนยันก่อนเขียน migration แรก**

| จุด | สมมติฐานที่ตั้งไว้ | ถ้าผิดจะเจ็บแค่ไหน |
|---|---|---|
| Job ↔ Course | 1 Job = 1 หลักสูตร = 1 รุ่น | 🔴 รื้อทุกตารางที่ผูก Job |
| Job ↔ Session (วัน/รอบ) | 1 Job = N วัน × 2 รอบ (เช้า/บ่าย) | 🔴 กระทบ attendance + ชั่วโมง + เกณฑ์ผ่าน |
| Job ↔ Trainer | 1 Job = N วิทยากร (ค่าตอบแทนแยกคน) | 🟠 กระทบ booking + ต้นทุน |
| Participant ↔ Enrollment | คน 1 คนใช้ซ้ำข้ามงาน (มีประวัติรวม) | 🟠 กระทบวุฒิบัตร + ประวัติรายบุคคล |

→ ทั้ง 4 ข้ออยู่ใน `01-requirements.md` §6–§7 แล้ว **ต้องให้ลูกค้ายืนยันเป็นลายลักษณ์อักษรก่อน M1**

## L3 🔴 สายข้อมูลขาดเงียบ ๆ (ฟิลด์บังคับที่ไม่มีใครกรอก)

**อาการ** — หน้าจ่ายงานเลือกได้แค่ทะเบียนรถ `driverId` เลย **เป็น null เสมอ** ผลคือ
**งานไม่เข้าแอปคนขับเลย** ทั้งที่ทุกเทสต์ผ่านหมด — เพราะไม่มีเทสต์ไหนเดินครบเส้น

**TrainFlow ทำแทน** — ทุก vertical slice ต้องมี **integration test ที่เดินครบเส้นจากต้นทางถึงปลายทางจริง**
เช่น *สร้าง Job → จองวิทยากร → วิทยากรยืนยัน → เห็นงานในหน้าวิทยากร* ต้องเป็นเทสต์เดียวที่รันจบ
(ไม่ใช่เทสต์ service ละตัว) และหน้าจอปลายทางต้องมีจริงก่อนถือว่าโมดูลจบ

---

## L4 🔴 ข้อมูลเดียวกันเก็บ 2 ที่ แล้วไม่ sync → เอกสารที่ส่งลูกค้าผิดเงียบ ๆ

**อาการ (ADR 0001)** — "รถตามแผน" (`Assignment.vehicleId`) กับ "รถที่ขับจริง" (`DriverShift`)
ไม่เคยไหลกลับหากัน ผลคือ **ทะเบียนบนใบวางบิลที่ส่งลูกค้าผิด** · เลขไมล์เข้าคันผิด ·
รายงานกำไรรายคันผิด — *"ทั้งหมดเกิดขึ้นเงียบ ๆ ไม่มีอะไรฟ้อง"*

**TrainFlow — คู่ "แผน vs จริง" ที่ต้องแยกให้ชัดตั้งแต่ data model และระบุว่าใครอ่านตัวไหน**

| คู่ | ค่าแผน | ค่าจริง | เอกสารปลายทางอ่านตัวไหน |
|---|---|---|---|
| ชั่วโมงอบรม | ชั่วโมงตามหลักสูตร | เวลาเริ่ม–จบที่วิทยากรบันทึก | **วุฒิบัตร/รายงาน = ค่าจริง** |
| วิทยากร | คนที่จองไว้ | คนที่มาสอนจริง | **รายงาน + ต้นทุน = คนที่มาสอนจริง** |
| จำนวนผู้เข้าอบรม | จำนวนที่ลูกค้าแจ้ง/ที่ลงทะเบียน | จำนวนที่เช็คอินจริง | **ใบวางบิล/รายงาน = ต้องระบุให้ชัดว่าใช้ตัวไหน** |
| สถานที่ | ที่ระบุในใบเสนอราคา | ที่จัดจริง | รายงาน = ค่าจริง |

> ห้ามใช้ฟิลด์เดียวแล้ว "เขียนทับ" — ทำให้ตามรอยไม่ได้ว่าแผนเดิมคืออะไร

---

## L5 🔴 สร้างของที่ไม่มีคนขอ แล้วต้องถอดทิ้ง

**อาการ** — ต้องถอด **โหมด Offer** (ยิงงานให้คนขับกดรับ) ทิ้งทั้ง backend + UI ·
**สูตรคิดต้นทุนอัตโนมัติจากราคาน้ำมัน** ปิดทิ้ง (ของจริงลูกค้าพิมพ์ค่าจริงลง Excel) ·
**Customer Portal** ที่ทำเสร็จแล้วถูกจัดเป็น priority ต่ำสุด

**TrainFlow ทำแทน** — ก่อนทำทุกฟีเจอร์ ต้องตอบได้ว่า **"ใครขอ และอยู่บรรทัดไหนของ requirement"**
ตอบไม่ได้ = ไม่ทำ. ห้ามใส่ "ความฉลาด" (auto-suggest, สูตรอัตโนมัติ) ที่ยังไม่มีคนขอ —
**ทำช่องกรอกตามจริงก่อนเสมอ** แล้วค่อยเพิ่มสูตรเมื่อรู้ว่าลูกค้าคิดยังไงจริง ๆ

---

## L6 🟠 ของที่ควรมีตั้งแต่ฐานราก แต่ไปเพิ่มทีหลัง = แพง

**อาการ** — ไม่มี **ระบบไฟล์แนบ** เลยจนถึง M8 (มีแค่อัปโหลดโลโก้) พอลูกค้าขอรูปหลักฐานหน้างาน
ต้องมาวางระบบ storage + สิทธิ์ + ตัวลบไฟล์ตอนหลัง

**TrainFlow ทำแทน** — สิ่งเหล่านี้อยู่ใน **M0/M1 ตั้งแต่แรก** เพราะเป็นแกนของ killer feature:
- **File/Object storage** (รูปกิจกรรม · เอกสารประกอบ · PDF วุฒิบัตร/รายงาน · ไฟล์รับรองวิทยากร)
- **ตัวสร้าง PDF ภาษาไทย** (ฟอนต์ฝังในภาพ/เอกสาร) — วุฒิบัตรและรูปเล่มรายงานคือหัวใจของสินค้า
- **ระบบแจ้งเตือน** (แม้ MVP จะส่งแค่อีเมล ก็ต้องมีตาราง log + ตัว abstract ช่องทางไว้)
- **สิทธิ์ระดับการกระทำรวม `EXPORT`** — dcs-tms เพิ่งมาแยกตอน M8 ว่า *"ดูบนจอได้ ≠ โหลดไฟล์ออกไปได้"*

## L7 🟠 เอกสารออกแบบ drift จากโค้ด

**อาการ (code review S1)** — migration ลบ `preorder*` ทิ้งแล้ว แต่ `02-system-design.md`
ยัง document ฟิลด์และ endpoint ที่ไม่มีอยู่จริง และของใหม่ไม่ถูก document เลย
ทั้งที่ `CLAUDE.md` เขียนกติกาไว้ชัดว่าต้องอัปเดต

**TrainFlow ทำแทน** — ด่านตรวจอัตโนมัติ (`/acceptance-check` แบบ dcs-tms) ต้องมาตั้งแต่ **M1 ไม่ใช่ M7**
และ CI ต้องแดงเมื่อเอกสารไม่ตรงโค้ด — กติกาที่ไม่มีเครื่องตรวจ = กติกาที่ไม่มีอยู่จริง

## L8 🟠 ตัวเลขสรุปไม่ตรงกับหน้ารายละเอียด

**อาการ (S2)** — Dashboard `ordersToday` ใช้เงื่อนไขคนละชุดกับกระดานงาน → ตัวเลขไม่มีทางตรงกัน
ทั้งที่ `CLAUDE.md` เขียนว่า "ต้องตรงกับกระดาน"

**TrainFlow ทำแทน** — ตัวเลขบน Dashboard/รายงาน **ต้องเรียก helper/query ตัวเดียวกับหน้ารายละเอียด**
และต้องมีเทสต์ที่ **เทียบตัวเลขสองหน้าให้เท่ากัน** (สำคัญมากเพราะระบบนี้มีตัวเลขซ้ำหลายที่:
จำนวนผู้เข้าอบรม · ชั่วโมง · pass rate · กำไร โผล่ทั้งหน้า Job, Dashboard, รูปเล่มรายงาน)

## L9 🟠 input ไม่ validate → จอเพี้ยนแบบเงียบ ๆ

**อาการ (S4)** — `?d=` ไม่ validate ทำให้ "บอร์ดวันเดียว" กลายเป็น "บอร์ดทุกวัน" โดยไม่มี error

**TrainFlow ทำแทน** — **fail loud เสมอ**: parameter ที่ parse ไม่ได้ = 400 พร้อม error code
ห้าม fallback เงียบ ๆ · ห้ามคำนวณเป็น 0 เมื่อข้อมูลไม่พอ (ใช้ pattern `calcStatus=BLOCKED` + `blockReason`
แบบที่ dcs-tms ใช้กับ costing — เอามาใช้กับ **การตรวจเกณฑ์ผ่าน** และ **การสร้างรายงาน** ของเรา)

## L10 🟠 บั๊กที่เทสต์ไม่เจอ แต่ "บอทเล่นหน้าจอจริง" เจอ

**อาการ** — ตอน M8 เอาบอท headless Chrome ไล่กดจอจริง เจอบั๊ก 4 ข้อรวด ที่ unit + integration
(474 เทสต์ · coverage 100%) ไม่เจอ เช่น รถที่เข้าเกณฑ์แต่คะแนนอันดับ 6 ลงไป**หายจากจอ**

**TrainFlow ทำแทน** — `.claude/agents/e2e-tester.md` (ยกมาแล้ว) ต้องเริ่มใช้ **ตั้งแต่โมดูลแรกที่มีหน้าจอ**
โดยเน้นเส้นทางที่ข้ามบทบาท: coordinator จอง → **วิทยากรเห็นงานบนมือถือจริงไหม** →
ผู้เข้าอบรมสแกน QR ได้จริงไหม → วุฒิบัตรออกจริงไหม

## L11 🟢 ของที่ dcs-tms ทำถูก — ยกมาใช้ทั้งดุ้น

| เรื่อง | ทำไมถึงถูก |
|---|---|
| **Contract 3 ไฟล์เป็น SSOT** (`openapi.yaml` · `schema.prisma` · `shared-types`) + CI ตรวจ | กัน agent/คนหลง context ได้จริง |
| **Integration test ยิง Postgres จริง ไม่ mock Prisma** | สิ่งที่ต้องพิสูจน์คือ tenant auto-filter, transaction, partial-unique, optimistic lock — mock พิสูจน์ไม่ได้ |
| **tenant auto-filter ที่ Prisma layer** (`prisma.scoped`) | โปรแกรมเมอร์ลืมใส่ `where tenantId` ไม่ได้แม้อยากลืม |
| **เงินเป็น `Decimal(14,2)` ห้าม Float** | — |
| **state-transition guard เป็นตารางใน shared-types** | สถานะข้ามขั้นถูกปฏิเสธที่ API ไม่ใช่แค่ซ่อนปุ่ม |
| **soft-delete master ทุกตัว** (`MASTER_IN_USE`) | ลบ master ที่มีประวัติแล้วเอกสารเก่าพัง |
| **Idempotency-Key บน mutation ที่เกี่ยวเงิน** | กันกดซ้ำ/เน็ตหลุดแล้วโพสต์ซ้ำ |
| **ค่าที่ยังไม่สรุป → วัดเก็บไว้ก่อน คิดเงินทีหลัง** (detention) | ไม่บล็อกงาน และไม่ต้องรื้อเมื่อได้คำตอบ |
| **ADR สำหรับการตัดสินใจที่รื้อยาก** | ตามรอยได้ว่าทำไมถึงเลือกทางนี้ |

## L12 🟢 ปฏิบัติการที่ต้องรู้ล่วงหน้า (เจ็บมาแล้ว)

- **Postgres enum:** `ALTER TYPE ... ADD VALUE` ต้อง**อยู่ลำพังในไฟล์ migration เดียว** (รันร่วม transaction อื่นไม่ได้)
- **วันที่:** ฟิลด์ที่เป็น "วัน" ใช้ `@db.Date` ไม่ใช่ timestamp · เวลาอ่านเป็น **wall-clock Asia/Bangkok**
  · **ปฏิเสธปี พ.ศ. ที่ input** แล้วค่อยแปลงเป็น พ.ศ. ตอนแสดง/พิมพ์เอกสารเท่านั้น
- **coverage:** dcs-tms ต้องเติมชื่อไฟล์ใหม่ลง `thresholds` ทุกครั้ง (ลืมแล้วเงียบ) →
  **TrainFlow ตั้ง global threshold ตั้งแต่ไฟล์แรก** จะได้ไม่ต้องพึ่งความจำ
- **UX:** ฟอร์มยาวห้ามอยู่ใน popup (ผู้ใช้เลื่อนเมาส์ออกแล้วข้อมูลหาย) → ใช้หน้าเต็ม
- **ไฟล์ข้อมูลจริงของลูกค้า** (Excel/รูป/PDF) ห้ามหลุดขึ้น git — `/ship` มีด่านกันไว้แล้ว ห้ามข้าม

## สรุปเป็นกติกาที่บังคับใช้ใน TrainFlow

1. ไม่มีคำตอบของคำถาม 🔴 → **ไม่เริ่ม migration แรก**
2. ทุก slice ต้องมีเทสต์ที่เดินครบเส้นถึงหน้าจอปลายทาง
3. แยก "ค่าแผน" กับ "ค่าจริง" เสมอ และระบุว่าเอกสารปลายทางอ่านตัวไหน
4. ไม่มีคนขอ = ไม่ทำ · ไม่มีปลายทาง = ไม่เก็บฟิลด์
5. ข้อมูลไม่พอ → **BLOCKED + เหตุผล** ไม่ใช่ 0 เงียบ ๆ
6. เอกสาร/สิทธิ์/ไฟล์แนบ/PDF/แจ้งเตือน = ฐานราก ทำตั้งแต่ M0–M1
7. เครื่องตรวจต้องมาพร้อมกติกา (CI + acceptance-check + e2e bot ตั้งแต่โมดูลแรก)
