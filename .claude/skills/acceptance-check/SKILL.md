# /acceptance-check — เอกสารตรวจรับยังตรงกับโค้ดไหม

เป้าหมาย: บอกผู้ใช้ว่า **หน้าไหนต้องกลับไปตรวจซ้ำ** และเพราะอะไร. ผู้ใช้ไม่ถนัด terminal — **รันคำสั่งให้เอง**.
สกิลนี้ **ห้ามแก้ไฟล์เอกสาร** — ถ้าต้องแก้ ให้เสนอผู้ใช้ว่าจะสั่ง `/acceptance ที่เปลี่ยน` ต่อไหม.

## 1. รันตัวตรวจ
- `npx tsx scripts/gen-acceptance.ts --check`
- อ่านผลทั้งหมด (❌ = ผิดพลาด ต้องแก้ · ⚠️ = เตือน) — **อย่าเทผลดิบให้ผู้ใช้อ่าน** ต้องแปลเป็นภาษาคน

## 2. แปลรหัสด่านเป็นภาษาคน
| ด่าน | แปลว่า |
|---|---|
| A | มีหน้าจอในระบบที่ยังไม่มีเอกสาร (หรือหน้าใหม่ยังไม่ถูกลงทะเบียนใน `scripts/acceptance/registry.ts`) |
| B | เอกสารอ้างคอลัมน์ที่ **ไม่มีอยู่จริง** ในฐานข้อมูล → เอกสารผิด หรือคอลัมน์ถูกลบ/เปลี่ยนชื่อ |
| C | เอกสารอ้างไฟล์/ฟังก์ชันที่หาไม่เจอ → โค้ดถูก refactor หลังเขียนเอกสาร |
| D | หน้า master มีช่องที่บันทึกได้จริงแต่ไม่มีในตารางเอกสาร → เอกสารตกหล่น |
| E | ข้อมูลอัตโนมัติ (สิทธิ์/endpoint/error/config) ไม่ตรงกับโค้ดปัจจุบัน → แค่รีเฟรชก็จบ |
| F | ไฟล์ต้นทางถูกแก้หลังเอกสารถูกตรวจ → **logic อาจเปลี่ยน ต้องอ่านซ้ำด้วยคน** |
| G | มีข้อมูลที่ดูเหมือนข้อมูลจริงของลูกค้า (เลข 13 หลัก / เบอร์โทร) อยู่ในเอกสาร → ต้องเอาออก |

## 3. หาสาเหตุก่อนสรุป (สำหรับ ❌ ทุกข้อ)
- ด่าน B/C/D: เปิดไฟล์จริงดูว่า **เอกสารผิด** หรือ **โค้ดเปลี่ยน** — สองอย่างนี้ผู้ใช้ต้องตัดสินใจต่างกัน
- ด่าน F: `git log --oneline -5 -- <ไฟล์ที่เตือน>` เพื่อดูว่าเปลี่ยนอะไร แล้วสรุปเป็นประโยคเดียวว่า
  "แก้เรื่อง X → ต้องอ่านข้อ 5/6 ของหน้านั้นซ้ำ" · ถ้าเป็นแค่จัดรูปแบบโค้ด ให้บอกว่าไม่กระทบ

## 4. จัดกลุ่มผลให้ผู้ใช้
1. **ต้องแก้เอกสาร** (เอกสารพูดไม่ตรงกับโค้ด) — ระบุหน้า + ข้อที่ต้องแก้
2. **น่าจะโค้ดผิด/หลุด** (เอกสารถูก แต่โค้ดทำไม่ตรงกฎที่ตกลงไว้) — ชี้ไฟล์ + บรรทัด ให้ผู้ใช้ตัดสิน
3. **หน้าใหม่ที่ยังไม่มีเอกสาร**
4. **แค่รีเฟรช** (ด่าน E) — บอกว่าสั่ง `/acceptance ที่เปลี่ยน` แล้วจบ

## 5. รายงานผล
สรุปสั้น: กี่หน้าตรวจ · ผ่านกี่หน้า · ต้องแก้กี่หน้า (เรียงตามความสำคัญ) · %checklist ที่ผู้ใช้ติ๊กไปแล้ว
(ดูจาก `docs/acceptance/README.md`) แล้วปิดท้ายด้วยข้อเสนอ 1 บรรทัดว่าควรทำอะไรต่อ.
